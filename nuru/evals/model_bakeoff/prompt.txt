# Battery Life Modeling

# Battery Life Modeling

## Core equations
- Average current: I_avg = Σ (I_k · d_k), where d_k is the fraction of time in state k, Σ d_k = 1
- Life (hours) = (C_nominal · η_usable) / I_avg
- Peukert (for lithium primary cells it's basically ≈1, but let's pretend): t = H · (C / (I · H))^k
- Self-discharge Li-SOCl2: ~1%/year. Not negligible over 10 yr.
- Duty-cycle-weighted energy per report: E = V · (I_tx·t_tx + I_rx·t_rx + I_sleep·t_sleep)

# UART Ring Buffer Snippets

# UART Ring Buffer Snippets

Code review bait. There are at least two bugs in the snippet below. Model: find them.

```c
#define RB_SIZE 256

typedef struct {
    uint8_t buf[RB_SIZE];
    volatile uint16_t head;
    volatile uint16_t tail;
} ring_t;

static inline bool rb_put(ring_t *r, uint8_t b) {
    uint16_t next = (r->head + 1) % RB_SIZE;
    if (next == r->tail) return false;     // full
    r->buf[r->head] = b;
    r->head = next;
    return true;
}

static inline int rb_get(ring_t *r) {
    if (r->head == r->tail) return -1;     // empty
    uint8_t b = r->buf[r->tail];
    r->tail = (r->tail + 1) % RB_SIZE;
    return b;
}

// ISR
void USART1_IRQHandler(void) {
    uint8_t c = USART1->DR;
    rb_put(&rx_ring, c);      // ignores overflow
}
```

## Known issues (spoilers)
1. Overflow is silently dropped. No counter, no error flag
2. Returns `int` but mixes -1 sentinel with valid 0-255. OK actually, but call sites that store into uint8_t will break
3. No memory barrier on head/tail with multi-core or DMA. On a single M4 with volatile it's usually fine
4. Capacity is RB_SIZE − 1 = 255, not 256. Off-by-one in my documentation

## Throughput math
At 115200 baud 8N1: 11520 bytes/s → one byte per 86.8 µs. With RB_SIZE=256, a full buffer represents 22.2 ms of data. If the consumer task runs every 50 ms (modem_fsm period) → overflow! Buffer needs ≥ 11520 · 0.05 = 576 B minimum, so pick 1024.

At 921600 baud: 92160 B/s → 1024 B fills in 11.1 ms. Consumer must run at least every ~5 ms or use DMA with idle-line detection.

# Battery Life Modeling Revised

# Battery Life Modeling (Revised)

Supersedes the earlier note. Reconciles the two architectures.

## Two architectures, done properly
**A. Always-connected (eDRX, no PSM):** I_avg ≈ 5.35 mA (from earlier table, overlap not corrected). Life = 30.4 Ah / 5.35 mA = 5682 h ≈ 237 days.

**B. Periodic attach, modem fully off between reports:** ≈ 1.53 Ah/year → naive 19.9 years.

## Realistic bounds for B
- Self-discharge: 1%/yr → over 10 yr the cell loses ~10% just sitting. Reduces usable capacity: 30.4 · 0.9 ≈ 27.4 Ah at year 10
- Passivation voltage delay at cold: can brown out the modem TX burst below −20 °C → extra retries → more charge per report. Assume +40% Q_report at cold: 602 mC → 843 mC
- Assume 25% of reports need a retry (weak signal, cf. Run 3 at 1410 mC): E[Q] = 0.75·602 + 0.25·1410 = 451.5 + 352.5 = 804 mC
- Charge/year = 8760 · 0.804 C = 7043 C = 1.956 Ah, plus sleep 0.061 Ah → 2.02 Ah/yr
- Life ≈ 27.4 / 2.02 ≈ 13.6 years, capped by shelf life (~10 yr practical). So in B the battery is not the limiting factor.

## Conclusion (tentative)
Requirement of 3 years is met with margin only if the device uses periodic attach or PSM truly works. Always-connected fails by 5x.
Sensitivity: reports/hour going from 1 → 6 multiplies the active charge by 6 → Life ≈ 27.4 / (6·1.956 + 0.061) ≈ 2.3 years. Fails 3-year target. Worth showing to the manager.

## Still unknown
- Actual reporting interval the product team wants (nobody has said)
- Whether latency requirements force always-connected (alarm path!). If a gas alarm must reach the cloud in < 5 s, periodic attach may be unacceptable. This is the real tension.
